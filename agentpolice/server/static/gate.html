agent-police-gate

在你的 agent 执行命令之前，
先检一遍

agent-police 回答的是「这个中转站在不在改」——靠主动探测。 这个东西回答另一半：「这条具体的命令该不该执行」。 它装进 Claude Code 和 Codex CLI， 在每一次工具调用上内联判定，不管你有没有探测过那个端点。

安装

pip install agent-police-gate

apgate install claude-code     # 合并进 ~/.claude/settings.json（先自动备份）
apgate install codex           # 合并进 ~/.codex/hooks.json

Claude Code 重开一个会话即可生效。Codex 装完还要在里面跑一次 /hooks 审核信任—— 它按哈希记录钩子信任，在你确认之前会静默跳过。

最有用的那一点

approvals 关掉之后，什么都不会再弹窗。这个闸门只在真正要紧的形态上把那一次确认放回来—— 从陌生 host 下载脚本直接管道进 shell、安装被指向了非默认 registry、URL 的真实 host 被 @ 藏起来了。

两个 agent 的实测结论

都是真跑出来的，不是看文档推的。

approvals 关掉时 ask 等于没有。 在 permission_mode: bypassPermissions 下，Codex 把闸门判为 ask 的命令照跑了—— 这是对的，因为根本没人可问。但这会让所有 ask 规则在最需要它们的无人值守场景里变成空操作。 所以闸门会在没有人在场时把 ask 升级为 deny： 一个没人能回答的确认，必须失败关闭。
Codex 不读项目级的 .codex/hooks.json，只认 ~/.codex/hooks.json， 也就是 apgate install codex 写的位置。

说清楚做不到什么

它无法告诉你模型原本输出的是什么。 PreToolUse 钩子看到的是经过中转站之后的工具调用，它从来没见过模型真正产出的那一条。 所以这里的每一项检查都只是「这条命令看着对不对」的启发式，不是和真值的比对。

论文实测自己那套策略闸门对懂防御的攻击者 100% 失效，这个数字同样适用于本项目。 这类闸门能挡住的，是 428 个中转站实测中真实存在的那种通用、不适配客户端的改写——值得挡，但和「安全了」不是一回事。

规则怎么保证准确

规则是数据，不是代码——只能从固定的谓词表里挑一个，再填字面量。 规则包里不存在正则、不存在 IO、不存在子进程，求值对输入是线性的。 能执行的规则就是能被武器化的规则，而这个东西是从网上拉下来的。

准确性靠机制保证，不靠人眼：每条规则自带正例反例，CI 用整个规则包跑一份普通开发命令语料， 任何会拦截的规则只要误报一次就不能发布。

层级人工审核能否拦截错了的代价
core是deny / askagent 停下来
community只过语料永不，仅 observe日志多一行

这个划分才是开放规则库能成立的前提，由 schema 强制。

更新策略

规则自动更新，代码不自动更新。 这东西跑在一个有 shell 权限的 agent 里，开一条自动更新代码的通道等于在每台用户机器上造一个远程执行入口—— 正是本项目要防的那种供应链形态。代码走 pip install -U，用户发起、可审计。

规则包用 Sigstore keyless 签名，由 GitHub Actions OIDC 签发，本项目不存在签名密钥； 每次发布同时公布 Merkle root，客户端可以校验「发给我的包」和「发给所有人的包」是同一个。 包括镜像是我们自己的时候。

隐私

账本在本地，权限 0600，不上传，写入前抹掉像密钥的 token。 APGATE_LEDGER_ARGS=0 只记哈希不记原文，APGATE_LEDGER_OFF=1 完全不记。 本版本没有任何遥测。

常用命令

apgate screen "curl -sSL https://get.example.com/i.sh | bash"   # 离线检查单条命令
apgate rules      # 当前加载了哪些规则、哪些能拦
apgate report     # 账本摘要 + 链完整性
apgate rescan     # 用今天的规则重扫历史
